Goal orchestration for coding agents

Loop a coding agent until the goal is verifiably met.

Hand goaly a goal. It freezes what "done" means, then loops your agent against that bar until it's actually done — a bar the agent can't weaken to pass. 

$ npm i -g goaly

1 Freeze the bar

The success check is hashed and frozen before the loop starts — the agent can't weaken its own test to finish.

2 Two keys for DONE

Done means both turn: the frozen check passes and an independent, refute-first reviewer doesn't veto.

3 Fail closed

Anything that errors or returns garbage is a fail, never a false green. The control loop makes zero LLM calls.

And there's more

Everything else, one line each.

  • Best-of-N attempts--candidates N races N isolated attempts per iteration and keeps the one that climbs furthest.
  • Parallel waves--parallel-phases runs independent plan phases concurrently and re-verifies every merge. A phased plan is a dependency DAG, not a list: each phase names itself with id and declares what it needs with dependsOn, so “C needs A and B, D needs only A” is expressible and checked — an unknown id, a self-reference, a cycle or a forward edge is a typed, fail-closed plan-parse failure, never a silently linearized plan. goaly then runs each topological frontier (every phase whose dependencies have completed) as one wave, recomputing it after each merge and on --resume so no completed phase repeats. Independence is declared instead of inferred from adjacency, and the graph is frozen into planHash like everything else.
  • Named worktrees--worktree isolates the whole run in its own checkout — your main tree is never touched.
  • Non-git mode--workspace-mode file runs goaly in a plain directory with a content-addressed manifest; no git init required.
  • Adversarial review--adversarial red-teams the contract before Seal and attacks every green before Sign-off.
  • Satisfiability criticRed-teaming asks whether a lazy worker could pass the bar without meeting the goal. This asks the mirror question, and it is on by default: before the freeze, one call checks whether a correct, complete implementation could still FAIL the authored bar — a call-count assertion made after mockRestore() already cleared mock.calls, a bar pinned to one file layout instead of observable behavior, an assertion on timing, ordering, ids or float equality. A frozen bar nothing can satisfy costs the entire run; the guard costs one call. Findings are told to make the bar satisfiable, never easier — it must still be red on today's tree. --no-satisfiability-critic opts out.
  • Contract dry runThe positive control, and the one guard that answers by execution instead of asking a model its opinion — also on by default. Pre-flight already proves the frozen bar is RED on today's tree; nothing proved it can ever go GREEN. So before the freeze, the compiler also writes a throwaway reference implementation, drops it into a scratch copy of your workspace beside the authored verification files, and runs the contract's deterministic rungs there. Green → the copy is destroyed and the contract freezes unchanged. Red → the bar is defective: the freeze is refused and the failure feeds the same bounded re-author loop as a compile failure. The reference implementation never reaches your workspace, the run diff, or any worker prompt — handing the worker a solution would defeat the run, so the scratch copy never duplicates a symlink back into your tree, and the refusal fed to the author is a structured summary — the exit code, the failing rung, lines naming only the frozen files, and at most one bounded assertion line — with everything else dropped, including lines that name no file (a runner reds by printing the source of the code under test, which on a red is the reference, and a bare traceback line is exactly how that source escapes a per-line blacklist). The scratch commands run under the same --sandbox jail and network policy as the verifier seam. Fail-open on any infrastructure error, so it can only reject a bar or step aside. --contract-dry-run false opts out.
  • Independent second keyThe Sign-off approver never inherits the coding agent's --model where the provider has one of its own, so the two keys are not drawn from one model by default; the swap is announced. When only one model exists, the run is recorded as SELF-JUDGED (a typed degraded mode) in the run header, the end-of-run summary and goaly runs show, so a DONE nobody independently reviewed is labelled wherever it is reported. And when the approver sits on the provider's own default — a model id goaly cannot resolve, so it cannot compare the two keys at all — the run is labelled INDEPENDENCE-UNVERIFIED rather than reported as independent. --approver-model removes both.
  • Web UIgoaly ui is a local control center: a mission dashboard, a live run pipeline, a session inspector into the agent's turns, and the Seal in a browser review station.
  • Watch & steerTail any live run, stop cleanly, resume with a note — you can add room, never lower the bar.
  • Crash-safeA write-ahead log survives a crash at any byte; budgets survive --resume.
  • Typed stuck abortsA no-progress run stops early with a reason that names its own fix — no-diff, repeat-failure, oscillation, harness crash, an unevaluable contract, or repeated turns that both hit --harness-timeout-ms and changed nothing (raise the cap, or set --harness-idle-timeout-ms so a still-working turn isn't guillotined). A repeat-failure streak can be re-adjudicated as a CONTRACT_DEFECTIVE contract fault rather than a worker fault — see below.
  • Contract-fault adjudicationContract soundness is otherwise judged exactly once, at t=0, against a tree with no implementation in it — the moment of least evidence. For an assertion no implementation can satisfy, that observation is genuinely ambiguous: it looks exactly like an honest "not written yet" red. So goaly asks again when the evidence exists. When a repeat-failure streak is about to abort and the repeated signature names one of the frozen authored check files on a tree the worker has demonstrably built out, one read-only call (at most once per run) asks whether any correct implementation could pass that check. If not, the run aborts as CONTRACT_DEFECTIVE, naming the file and saying plainly that your implementation may be correct and the tree is worth keeping — instead of telling you to raise --stuck-repeat-threshold, which cannot help. Diagnosis only: this path can never reach DONE, never re-authors the frozen bar, and fail-closes to today's abort on no LLM, an error, or any uncertainty.
  • Re-contract successor runThe recovery a CONTRACT_DEFECTIVE verdict earns you, printed verbatim in the abort: goaly --from-run <id> --recontract. It keeps the tree (the implementation is the valuable artifact), inherits the predecessor's frozen goal, and re-runs COMPILE with the defect report as authoring feedback — the same free-text channel a Seal "revise" uses — then freezes a new contract with a new contractHash under a new run id. No contract is ever mutated: one run owns exactly one frozen bar for its whole life, and evolution happens between runs, recorded — the successor's header carries predecessorRunId, predecessorContractHash and the verdict, and goaly runs show prints the chain. Guarded on all sides: only a real (write-ahead, Zod-parsed) defective adjudication can reach it, so the worker can never trigger it and no worker text feeds the re-authoring; a re-authored bar that already passes faces a fail-open negative control before a single worker token is spent — and that control is shown what it is judging: the re-authored rungs/rubric, the contents of the re-authored verification files, the predecessor's bar and the adjudicated defect, all untrusted-fenced, so “was this softened?” is answered by comparison rather than guessed from filenames (missing or unreadable evidence only weakens the control, it never aborts a run); and --max-recontracts (default 1) bounds the chain from the run log, not per process, so a bar cannot be ratcheted downward across generations.
  • Defect corpus (cross-run learning)Every other feedback channel in goaly dies with the run that produced it, so the compiler would re-author the same impossible bar forever. When a run adjudicates a bar CONTRACT_DEFECTIVE, goaly appends one compact record to ~/.goaly/defects.jsonl — the adjudicator's generalized anti-pattern and assertion shape, the language/runner derived from the frozen contract, and the contractHash + runId for provenance. Never your source, never the diff, never the failure text. Future --generate authoring receives the entries relevant to this workspace as a bounded “known false-red patterns — do not author these” section, and each injected pattern is logged so a run says which local state shaped its bar. The safeguards are structural, not conventions: only an adjudicated defective verdict can mint a record (nothing else even type-checks against the append), the builder has no input through which worker text could arrive, and the strict schema has no field for iterations, duration, spend or severity, so “this was hard” can never arrive as data and become “author an easier bar”. The primary defense is the fence, not the signature: a pattern is model-authored text entering another model's prompt, so the section is wrapped in a random-nonce UNTRUSTED fence with the rule restated in the compiler's system prompt — the same treatment the diff gets at every other seam — and goaly's own framing, phrased as impossibility, stays outside it. That is what contains a hostile line whether or not its provenance is real. Signing is a second, narrower line: the corpus sits outside your workspace (outside the run diff, the frozen-file integrity guard, and everything Seal shows you), so every record is HMAC-signed with a key minted on first use beside it (~/.goaly/defects.key, owner-only) and carries a per-record nonce — any line that is missing a signature, altered, foreign, or a replayed copy of one already read is dropped or collapsed on read, and no single run can contribute more than three records. No key, no hints. Be clear about the limit: that closes hand-edited, copied-in and replayed lines, not the coding agent, which under the default --sandbox none runs as goaly's own uid and can read the key as easily as it could write the file — owner-only mode excludes other users, not a subprocess of ours. An active --sandbox policy masks ~/.goaly from the agent seam, and the injection log says in a trust field which of the two situations your run is in. The effort word list (hard, difficult, iterations, attempts, time, tokens, complexity) is refused on mint and on read, but it is a speed bump over 240 characters of prose, not a semantic filter — a paraphrase gets through, and the impossibility framing plus the fence are what actually hold. The section is phrased as impossibility, the corpus is fail-open (missing/corrupt ⇒ exactly today's behavior), and a corpus-shaped contract still faces the critics, Seal, the pre-flight negative control and both keys. Inspect it with goaly config defects list, reset it with goaly config defects clear, opt out with --no-defect-corpus. Local only — nothing is uploaded or fetched.
  • Stuck self-recovery--auto-remediate-stuck lets a long unattended run spend up to 3 bounded self-recoveries — a change-your-approach hint on a no-diff turn, one extra attempt on a repeat/crash streak — before stopping for you.
  • Sandboxing--sandbox jails the agent and the verify command, with per-seam network policy.
  • Follow-ups--from-run starts a new, re-verified goal that knows what just happened.
  • Autonomy profiles--mode review|hands-off|aggressive bundles the right flag combination for a whole autonomy posture; explicit flags always override, loudly.
  • Named presets--preset <name> selects a flag bundle by name: a language-neutral default ships built in and applies implicitly when no preset or mode is chosen (gap-filling only — config files and explicit flags always win; announced with --preset none as the off-switch), and "presets" in .goalyrc defines (or redefines) your own — persist "preset" to pick the one applied on every run. One word instead of N flags.
  • Dry run--dry-run resolves your flags and .goalyrc and prints the config a run would use — writing nothing and spending nothing.
  • Onboardinggoaly doctor reports what your environment is missing (Node, git, harness CLIs, config validity); goaly init writes a starter .goalyrc — interactive or headless. A shipped JSON Schema gives .goalyrc editor auto-completion, and goaly config validate gives the run-path verdict.
  • Harness autonomy--harness-autonomy lets the agent install and build for a from-scratch goal; if it refuses an action, the abort names the fix instead of blaming your install. Raising it auto-pins the reviewed diff to the run-start commit, so an agent git commit stays visible to both keys (and the pin survives --resume).
